# 용도 기반 색상 토큰 재정의 + 이동 요청 기능 적용

작성일: 2026-11-26
대상: `frontend/baro-app` (Expo SDK 54 / React Native / TypeScript)

## 왜 하는가

프로젝트 종료 후 회고에서, 프론트엔드 포트폴리오에 디자인 시스템 케이스 스터디를 싣기 위해 색상 토큰을 다시 정리한다. 참고한 글은 Adham Dannaway의 Figma 디자인 시스템 케이스 스터디(`adhamdannaway.com/portfolio/figma-design-system`)이며, 거기서 가져오는 것은 **색 이름을 용도로 짓는 규칙**과 **라이트/다크에서 대비를 일정하게 유지하는 원칙**이다.

포트폴리오에서 보여주려는 것은 "문제를 직접 찾아서, 범위를 판단하고, 재발을 막았다"이다. 그래서 이 작업의 결과물은 코드 변경과 함께 **측정값과 전후 증거**를 남겨야 한다.

이 문서는 코드 작업만 다룬다. 포트폴리오 글 자체는 이 작업의 결과(숫자, 화면)가 나온 뒤 별도로 다룬다.

## 현재 상태 (2026-11-26 `master` 기준 측정)

색상 정의는 `src/styles/colors.ts`에 두 층으로 있다.

- `Palette`: 색상명+단계로 지은 원시 값 (`gray600`, `violet600` 등 약 50개)
- `Colors.light` / `Colors.dark`: 의미 토큰 17개 (`text`, `primary`, `danger` 등). `useTheme()`이 현재 모드의 값을 돌려준다.

그런데 화면 코드는 의미 토큰을 거의 거치지 않는다.

| 색을 쓰는 방식 | `src` 전체 (`src/styles` 제외) | 그중 `features/move-request` |
|---|---|---|
| `theme.*` (의미 토큰) | 26곳 | 3곳 |
| `Palette.*` 직접 사용 | 463곳, 파일 118개 | 124곳 |
| 색상 값 하드코딩 (hex, `rgb()`) | 약 160곳 (136줄) | 약 86곳 (75줄) |

하드코딩 수치는 세는 방식(출현 횟수/줄 수)에 따라 달라진다. 작업 1단계에서 명령 하나를 정해 다시 세고, 그 값을 "작업 전" 기준으로 삼는다.

원인은 구조에 있다. 스타일은 `*.styles.ts`에서 `export const styles = StyleSheet.create({...})`로 한 번 만들어지는 고정 객체라 `useTheme()` 훅을 쓸 수 없다. 그래서 스타일 파일은 `Palette`나 값을 직접 쓰게 되고, 그 결과는 다음과 같다.

- `app.json`이 `userInterfaceStyle: "automatic"`이라 기기가 다크 모드면 `Screen` 배경과 `ThemedText`는 어두운 테마로 바뀌지만, 고정 스타일을 쓰는 대부분의 화면은 라이트 색 그대로 남는다.
- 같은 역할의 색이 여러 값으로 흩어져 있다. 예: 보조 글자색이 `Palette.gray500`(`#7b8091`), `#9599a7`, `#5c6070`, `Palette.gray600`으로 섞여 쓰인다.
- 실제 본문 글자색은 `Colors.light.text`(검정)가 아니라 `Palette.gray975`(`#14161c`)다. 의미 토큰의 값이 실제 화면과 어긋나 있다.
- 유틸 함수가 색 값을 직접 돌려준다. `features/move-request/utils/move-request.ts`의 `RequestTimelineStep.dotColor` / `labelColor`.

대비도 일부 미달이다 (WCAG 2.1 대비 공식으로 계산).

| 글자색 | 배경 | 대비 | 쓰이는 곳 |
|---|---|---|---|
| `#9599a7` | `#ffffff` | 2.84 | 타임라인·카드의 보조 설명 (11~12.5px), 앱 전체 16곳 이상 |
| `Palette.gray500` `#7b8091` | `#ffffff` | 3.93 | 보조 글자 |
| `Palette.orange600` `#d4553a` | `#fff2ef` | 3.72 | 상태 배지 글자 |
| `Palette.orange600` `#d4553a` | `#ffffff` | 4.07 | 경고 글자 |
| `Palette.blue600` `#3f7bd6` | `Palette.sky100` `#d5e6ff` | 3.31 | 완료 상태 배지 |

기타 확인한 사실:

- 테스트 러너가 없다 (`jest`, `vitest` 없음). 검증 명령은 `npm run typecheck`, `npm run lint`뿐이다.
- CI는 `Jenkinsfile`이 Node 20에서 `npm ci`와 `npm run typecheck`를 돌린다. 린트는 CI에서 돌지 않는다. `Jenkinsfile.cd`는 `expo export --platform web`으로 웹을 내보내 배포하므로, `src/app`에 추가한 라우트 파일은 배포 결과물에 포함된다.
- 이동 요청 화면 5개는 `src/components/ui`의 공용 컴포넌트로 조립되어 있고, 이들도 라이트 색이 고정되어 있다: `ScreenHeader`, `SegmentedControl`, `GradientScreenBackground`, `InfoRowCard`, `FormSectionLabel`, `AsyncStateView`, `BottomNavBar`. 구역 선택 모달은 `features/parking`의 `ParkingSpotMap` / `ParkingLegend`를 쓴다.
- 이동 요청 기능에는 `rgba()` 값이 9곳 있다: 모달 뒤 어둡게 깔리는 막, 사진 위 글자용 막과 글자 그림자, 그림자색, 반투명 흰색.
- `eslint.config.js`와 `eslint.config.ts`가 둘 다 있다. ESLint는 `.js`를 먼저 읽고, `.ts` 설정을 읽는 데 필요한 `jiti`가 의존성에 없다. 따라서 `no-console` 등이 들어 있는 `.ts` 쪽은 적용되지 않고 있을 가능성이 높다. 이 워크트리에는 `node_modules`가 없어 실행으로 확인하지는 못했다.
- 이동 요청 기능에는 목(mock) API가 없다. 화면을 보려면 로그인과 배포 서버(`EXPO_PUBLIC_API_BASE_URL`)가 필요한데, 프로젝트 종료 후라 서버가 살아 있는지 알 수 없다.
- `baro-app` 경로 기준으로 `master`가 `origin/develop`보다 17커밋 앞서 있다. 작업 기준은 `master`다.

## 목표

1. 색상 의미 토큰을 **용도 기반 이름 규칙**으로 다시 정의한다. 라이트/다크 값을 모두 갖는다.
2. 고정 스타일 파일에서도 테마 토큰을 쓸 수 있는 **구조**를 만든다.
3. `features/move-request` 전체와, 이동 요청 화면이 쓰는 공용 컴포넌트 7개(`ScreenHeader`, `SegmentedControl`, `GradientScreenBackground`, `InfoRowCard`, `FormSectionLabel`, `AsyncStateView`, `BottomNavBar`)를 새 토큰으로 옮긴다. 이 범위에서 `Palette` 직접 사용과 색상 값 하드코딩이 0이 되고, 이동 요청 화면이 다크 모드에서 처음부터 끝까지 어두운 테마로 보인다.
4. **린트 규칙**으로 재발을 막는다. 옮긴 폴더는 오류, 나머지는 경고.
5. **대비 자동 검사**를 명령 하나로 돌릴 수 있게 한다.
6. 포트폴리오에 쓸 **증거**를 남긴다: 전후 사용 횟수, 대비 검사 결과, 라이트/다크 전후 화면.

## 하지 않는 것

- 이동 요청 외 다른 기능의 스타일 이전. 경고로만 드러낸다. 구역 선택 모달 안의 `ParkingSpotMap` / `ParkingLegend`도 `features/parking` 소속이라 옮기지 않는다. 주차 도면은 칸 색 자체가 정보라서 별도 설계가 필요하다. 다크 모드에서 이 모달 안의 도면은 라이트 색으로 남는다는 점을 알려진 한계로 기록한다.
- `admin-web` 변경. 이름 맞추기는 다음 작업이다.
- 팔레트를 투명 색상 기반으로 다시 짜는 것, 상태 오버레이(hover/press layer). 참고 글에는 있지만 컴포넌트 구조까지 바꿔야 한다. 단, 지금 이미 쓰이는 반투명 막은 아래 `overlay.*` 토큰으로 옮긴다.
- 토큰 원본을 하나로 합쳐 RN용/웹용을 생성하는 파이프라인.
- 간격·타이포 토큰 변경. 이동 요청 스타일에는 `fontSize: 12.5`, `Spacing.md + 2` 같은 스케일 밖 값이 있지만 이번에는 건드리지 않고 "다음 개선"으로 기록만 한다.
- 새 런타임 의존성 추가 (NativeWind, unistyles 등).
- 원격 저장소 push, MR 생성. 로컬 브랜치 커밋까지만 한다.

## 실패로 보는 경우

- 라이트 모드에서 이동 요청 외 화면의 모양이 바뀐다. 기존 `Colors` / `useTheme()` / `ThemedText`의 `themeColor`는 값과 동작을 그대로 유지해야 한다. 공용 컴포넌트 7개는 라이트 값이 지금과 같아야 한다(매핑 표에서 승인된 변경 제외).
- 다크 모드에서 다른 기능의 화면이 지금보다 읽기 어려워진다. 공용 컴포넌트 7개가 어두운 테마로 바뀌면 그것을 쓰는 다른 화면도 영향을 받는다. 예를 들어 헤더 제목이 흰색이 되는데 그 화면 배경이 라이트로 고정되어 있으면 제목이 안 보인다. 공용 컴포넌트를 옮길 때 그것을 쓰는 화면 목록을 뽑아 다크 모드에서 글자가 읽히는지 확인한다.
- 팀원이 만든 토큰 기초를 지우거나 이름을 바꿔서, 다른 기능 코드가 깨진다.
- 승인받지 않은 색 변경이 라이트 모드 화면에 섞여 들어간다. 색이 바뀌는 곳은 모두 아래 "매핑 표 검토"를 거친다.
- 린트 규칙 때문에 기존 `npm run lint`가 오류로 실패한다. 옮기지 않은 폴더는 경고여야 한다.

## 검토한 방법

### 토큰을 어떻게 정리할 것인가

| 방법 | 내용 | 판단 |
|---|---|---|
| 값 그대로 등록 | 하드코딩된 값을 전부 팔레트에 추가 | 화면은 안 바뀌지만 어긋난 값을 공식화할 뿐이고, 다크 모드와 대비 문제는 그대로 남는다 |
| 기존 17개 토큰에 몇 개 추가 | `textTertiary`, `success` 등을 덧붙임 | 작업은 작지만 이름 규칙이 없어 다음 사람이 또 임의로 추가하게 된다 |
| **용도 기반 규칙으로 재정의** (선택) | `요소.톤.강조` 규칙으로 의미 층을 새로 짬 | 빠진 색이 규칙의 빈칸으로 드러나고, 이름만 보고 쓸 곳을 알 수 있다 |

사용자가 참고 글의 방식으로 정리하기를 원했고, 세 번째를 골랐다.

### 코드에 어디까지 적용할 것인가

| 방법 | 내용 | 판단 |
|---|---|---|
| 정의만 하고 코드는 그대로 | 문서와 토큰 표만 만듦 | 코드 증거가 없어 포트폴리오에서 약하다 |
| 앱 전체 이전 | 파일 118개 | 화면마다 확인이 필요하고, 팀 코드 전반을 건드린다. 포트폴리오 한 꼭지로는 과하다 |
| **기능 하나만 완전히 이전** (선택) | 이동 요청 기능 | 색 참조가 가장 몰린 기능(약 200곳)이라 전후 차이가 크고, 범위 판단 자체가 이야깃거리가 된다 |

### 고정 스타일에서 테마를 쓰는 구조 (작성자 판단)

| 방법 | 판단 |
|---|---|
| 색만 컴포넌트에서 인라인으로 덮어쓰기 (`AppButton` 방식) | 스타일이 두 파일로 갈라지고, 색 참조가 200곳이라 컴포넌트가 지저분해진다 |
| `PlatformColor` / `DynamicColorIOS` | 플랫폼별 코드가 필요하고 웹에서 안 된다. "Android·iOS·Web 공통" 원칙에 어긋난다 |
| 스타일 라이브러리 도입 | 새 의존성. 기능 하나를 위해 넣기에는 크다 |
| **스타일을 토큰을 받는 함수로** (선택) | `*.styles.ts`가 `createStyles(tokens)`를 내보내고 컴포넌트가 훅으로 받는다. 파일 위치 규칙(`AGENTS.md`)이 유지되고 새 의존성이 없다 |

## 설계

### 이름 규칙

`요소.톤.강조` (필요할 때만 `.상태`).

| 자리 | 값 | 설명 |
|---|---|---|
| 요소 | `text`, `icon`, `stroke`, `fill`, `background` | 색이 칠해지는 대상. `fill`은 버튼·배지·점처럼 요소 자체의 면, `background`는 화면·카드 같은 바탕 |
| 톤 | (중립은 생략), `brand`, `error`, `warning`, `success`, `info`, `inverse` | 색이 전하는 의미 |
| 강조 | `strong`, `weak`, `weaker` | 눈에 띄는 정도 |
| 상태 | `disabled` 등 | 기존 코드에 실제로 필요한 경우에만 만든다 |

TypeScript에서는 중첩 객체로 쓴다: `t.text.strong`, `t.text.error.strong`, `t.fill.brand.weak`, `t.stroke.weak`.

규칙에 맞지 않는 색은 다음 네 가지로 제한한다.

- `overlay.*`: 반투명 막. 모달 뒤 막(`overlay.scrim`), 사진 위 글자를 받치는 막 등 지금 쓰이는 용도만 만든다. 값은 `rgba`이며 토큰 정의 파일 안에서만 적는다.
- `shadow`: 그림자색. 지금 `shadowColor: Palette.gray975`로 쓰이는 값.

- `background.raised`: 카드처럼 떠 있는 면. 라이트에서는 흰색 + 그림자, 다크에서는 그림자가 보이지 않으므로 바탕보다 한 단계 밝은 면으로 높이를 표현한다 (참고 글의 "Depth done right").
- `gradient.*`: 화면 배경 그라데이션. 이동 요청 화면들이 상태별로 다른 그라데이션을 쓰므로 톤 이름을 따라 `gradient.brand`, `gradient.error` 식으로 둔다. 라이트/다크 값을 모두 갖는다.

### 토큰 초안 (라이트)

이동 요청 기능에서 실제 쓰이는 색을 규칙에 넣은 출발점이다. 최종 값은 아래 "매핑 표 검토"에서 확정한다.

| 토큰 | 출발 값 | 지금 쓰이는 형태 |
|---|---|---|
| `text.strong` | `#14161c` (gray975) | `Palette.gray975` |
| `text.weak` | `#60646c` (gray600) | `Palette.gray600`, `#5c6070` |
| `text.weaker` | 대비 4.5 이상인 회색으로 새로 정함 | `#9599a7`(2.84), `Palette.gray500`(3.93) |
| `text.inverse` | `#ffffff` | `Palette.white` (어두운 면 위 글자) |
| `text.brand` | `#5144d3` (violet600) | `#5c4fe0`, `Palette.violet600` |
| `text.error` | 대비 4.5 이상인 값으로 조정 | `Palette.orange600`(4.07), `#c8492e`(4.72) |
| `fill.brand.strong` | `#5144d3` | `Palette.violet600`, `#5c4fe0` |
| `fill.brand.weak` | `#ede9fd` 계열 | `#ede9fd`, `#eae8fb`, `Palette.violet100` |
| `fill.error.strong` | `#e5484d` (red500) | `#e5493d`, `Palette.red500` |
| `fill.error.weak` | `#fff2ef` (orange50) | `Palette.orange50`, `#fff0eb` |
| `fill.success.strong` / `.weak` | `#2fae9e` / `#dff3ef` | `Palette.emerald500`, `Palette.teal100`, `#e1f8f5` |
| `fill.info.weak`, `text.info` | sky100 / 대비 조정한 파랑 | `Palette.sky100`, `Palette.blue600`(3.31) |
| `fill.neutral.weak` | `#e2e0ec` 계열 | `#e2e0ec`, `#c9c4e8` (진행선, 비활성 점) |
| `stroke.weak` | `#e1e1e8` (gray200) | `Palette.gray300`, `Palette.lavender100` |
| `stroke.error` | `#ff8f6b` (orange400) | `Palette.orange400` |
| `background.neutral` | `#ffffff` | 화면 바탕 |
| `background.weak` | `#f7f6fb` (lilac25) | `#f7f6fb`, `#f5f4fb` |
| `background.raised` | `#ffffff` | 카드 면 `Palette.white` |

`warning` 톤은 이동 요청 기능에서 `error`와 구분해 쓰는 곳이 있을 때만 채운다(재촉 알림 등). 구분이 없으면 비워 둔다.

### 값을 정하는 기준

1. 팔레트에 같은 값이 있으면 그 단계를 가리킨다. 화면 변화 없음.
2. 팔레트 값과 눈으로 구분되지 않는 값은 팔레트 단계로 합친다.
3. 구분되는 값은 팔레트에 새 단계로 추가하고 토큰이 그것을 가리킨다.
4. 글자와 아이콘 토큰은 **쓰이는 배경 위에서 WCAG AA**를 만족해야 한다: 본문 글자 4.5:1, 큰 글자(18pt 이상 또는 굵은 14pt 이상)와 아이콘·테두리 3:1. 지금 미달인 값은 같은 색상 계열에서 기준을 넘는 가장 가까운 값으로 바꾼다. 이 경우 라이트 화면의 색이 조금 진해진다.
5. 다크 값은 같은 역할이 같은 대비 수준을 갖도록 정한다. 라이트에서 `text.weak`가 `text.strong`보다 한 단계 약하면 다크에서도 그래야 한다.

모든 의미 토큰은 `Palette` 단계를 가리킨다. 지금 `Colors.dark`에 있는 것 같은 값 직접 기입은 새 토큰에서는 하지 않는다. 다크용 값이 팔레트에 없으면 팔레트에 추가한다.

### 매핑 표 검토 (사용자 확인 지점)

이동 요청 코드를 고치기 **전에** 매핑 표를 만들어 사용자에게 보여준다. 표의 각 행은 다음을 담는다.

- 지금 값과 쓰인 횟수
- 옮겨 갈 토큰
- 새 값(라이트/다크)과 지금 값 대비 달라지는지 여부
- 해당 배경 위 대비

값이 눈에 띄게 달라지는 행(합치기, AA 조정)은 색 견본을 나란히 보여주고 사용자가 고른다. 사용자가 "AA 미달이어도 지금 값 유지"를 고르는 행은 그대로 두되, 대비 검사의 알려진 예외 목록에 사유와 함께 적는다. 이 표는 `docs/design-system/`에 남긴다.

### 코드 구조

**토큰 정의** — `src/styles/` 안의 새 파일.

- 라이트/다크 두 벌의 같은 모양 객체와 그 타입을 내보낸다.
- 기존 `Palette`, `Colors`, `ThemeColor`는 지우거나 이름을 바꾸지 않는다. `Palette`에는 단계를 추가만 한다.
- 기존 `Colors`의 값은 바꾸지 않는다. 다른 화면의 모양이 달라지면 안 된다.
- `Gradients`의 기존 키도 유지한다. 테마별 그라데이션은 새 토큰 쪽에 둔다.

**토큰을 받는 훅** — `src/hooks/`.

- 현재 모드의 토큰 객체를 돌려주는 훅.
- `createStyles` 함수를 받아 현재 모드의 스타일을 돌려주는 훅. 모드는 둘뿐이므로 모드별로 한 번만 만들어 재사용한다. 렌더마다 `StyleSheet.create`를 다시 부르지 않는다.
- 웹의 hydration 처리는 기존 `use-color-scheme.web.ts`를 그대로 따른다.

**스타일 파일** — 이동 요청의 `*.styles.ts`.

```ts
// 지금
export const styles = StyleSheet.create({
  stepDetail: { fontSize: 11, color: '#9599a7' },
});

// 바뀐 뒤
export const createStyles = (t: ColorTokens) =>
  StyleSheet.create({
    stepDetail: { fontSize: 11, color: t.text.weaker },
  });
```

색을 쓰지 않는 스타일 파일은 바꾸지 않는다.

**색을 돌려주는 유틸** — `utils/move-request.ts`.

`RequestTimelineStep`의 `dotColor` / `labelColor`(색 값)를 톤 이름으로 바꾼다. 유틸은 "이 단계는 `error`"라는 의미만 돌려주고, 컴포넌트가 톤을 토큰으로 푼다. 유틸에 색 값이 남지 않는다.

**SVG와 그라데이션** — `stroke="#d4553a"` 같은 SVG 속성과 화면 파일의 `*_GRADIENT` 상수도 토큰에서 가져온다.

### 린트

`eslint.config`에 규칙 두 가지를 넣는다. 새 패키지 없이 ESLint 기본 규칙으로 구현한다.

- 색상 값 문자열 금지: hex(`#rgb`, `#rrggbb`, `#rrggbbaa`)와 `rgb()` / `rgba()` / `hsl()` 문자열.
- `@/styles`에서 `Palette` 가져오기 금지.

적용 범위:

- `src/styles/**`: 규칙 없음. 토큰을 정의하는 곳이다.
- `src/features/move-request/**`와 옮긴 공용 컴포넌트 7개의 파일: **오류**.
- 그 밖의 `src/**`: **경고**. 다른 기능을 옮길 때마다 오류 목록에 폴더를 추가한다.

경고 메시지에는 대신 쓸 것을 적는다 (예: "색상 값 대신 `src/styles`의 토큰을 사용하세요").

두 설정 파일 문제는 먼저 실행해서 확인한다. 어느 파일이 적용되는지 확인하고, 적용되지 않는 쪽에만 있는 규칙(`no-console`, `no-explicit-any` 경고)을 적용되는 파일로 합친 뒤 하나만 남긴다. 합친 결과로 기존 코드에 새 **오류**가 생기면 그 규칙은 경고로 둔다.

### 대비 검사

`npm run check:contrast` 하나로 실행한다.

- 토큰 정의 파일에서 값을 직접 읽는다. 값을 스크립트에 따로 적지 않는다.
- 검사할 쌍(글자·아이콘 토큰 × 그것이 놓이는 배경 토큰)과 기준(4.5 또는 3)을 목록으로 선언한다. 라이트와 다크 모두 검사한다.
- 미달이 있으면 어느 쌍이 몇 대 일인지 출력하고 0이 아닌 코드로 끝난다.
- 알려진 예외는 사유와 함께 목록에 적고, 출력에 예외로 표시한다.
- 새 런타임 의존성 없이 만든다. 실행 방법(Node 24의 TypeScript 직접 실행 등)은 만드는 사람이 확인해 정한다. 테스트 러너를 새로 들이는 것은 이 작업 범위가 아니다.
- CI(Jenkins, Node 20)에는 연결하지 않는다. 로컬에서 돌리는 명령으로 둔다. `Jenkinsfile`은 건드리지 않는다.

### 미리보기 화면 (작성자 판단)

개발 빌드에서만 열리는 화면 하나를 추가한다. 웹 배포가 `src/app`의 모든 라우트를 내보내므로, 배포 빌드에서는 이 경로로 들어와도 내용이 보이지 않고 홈으로 돌려보내야 한다 (`__DEV__` 검사).

- 내용: 토큰 견본(이름과 값), 그리고 이동 요청의 대표 컴포넌트(타임라인 카드, 상태 배지, 진행 카드, 목록 카드)를 고정 데이터로 그린 것.
- 이유 1: 이동 요청 화면은 로그인과 서버가 있어야 열리는데 서버 상태를 알 수 없다. 이 화면이 있으면 서버 없이 라이트/다크를 확인할 수 있다.
- 이유 2: 포트폴리오의 그림(실제 컴포넌트에 토큰 이름을 붙인 그림, 라이트/다크 비교)의 원본이 된다.
- 라우트 파일은 `AGENTS.md` 규칙대로 화면을 다시 내보내는 얇은 파일로 두고, 실제 화면은 `src/features/` 아래 별도 폴더에 둔다.

서버에 접속할 수 있으면 실제 화면 5개(요청 목록, 작성, 전송 완료, 상세, 이력)도 확인한다. 접속할 수 없으면 그 사실을 결과에 적는다.

### 남길 증거

`docs/design-system/` 아래에 둔다.

- `tokens.md`: 이름 규칙, 토큰 표(라이트/다크 값), 쓰는 법. 이 문서가 시스템 설명서 역할을 한다.
- 매핑 표: 옛 값 → 토큰, 달라진 값과 이유.
- 전후 수치: 위 "현재 상태" 표와 같은 방식으로 다시 센 값. 세는 명령도 함께 적어 누구나 다시 셀 수 있게 한다.
- 대비 검사 결과: 작업 전 값으로 돌린 결과와 작업 후 결과.
- 화면: 라이트/다크, 작업 전/후. 작업 전 화면은 코드를 바꾸기 전에 먼저 찍어 둔다.

## 작업 순서와 확인 지점

1. 의존성 설치, `typecheck`·`lint` 현재 결과 기록, ESLint 설정 파일 확인. 작업 전 화면 저장.
2. 토큰 초안과 **매핑 표 작성 → 사용자 검토**. 여기서 색 변경을 확정한다.
3. 토큰 정의, 훅, 대비 검사 스크립트.
4. 미리보기 화면.
5. 이동 요청 기능 이전. 하위 폴더 단위로 나눠 진행한다.
6. 린트 규칙 적용.
7. 수치 재측정, 화면 저장, `tokens.md` 정리.

## 완료 기준

- `features/move-request`와 공용 컴포넌트 7개에서 `Palette` 직접 사용 0, 색상 값 하드코딩 0. 린트가 이를 오류로 강제한다.
- `npm run typecheck` 통과. `npm run lint`가 오류 없이 끝난다 (다른 폴더의 경고는 허용, 개수를 기록).
- `npm run check:contrast`가 라이트/다크 모두 통과하거나, 남은 미달이 사유와 함께 예외 목록에 있다.
- 미리보기 화면에서 이동 요청 컴포넌트가 라이트/다크 모두 읽을 수 있게 보인다.
- 이동 요청 폴더와 공용 컴포넌트 7개 밖에서는 색 관련 코드에 변경이 없다 (diff로 확인).
- 공용 컴포넌트 7개를 쓰는 다른 화면이 다크 모드에서 지금보다 읽기 어려워지지 않았다. 서버 없이 확인할 수 없는 화면은 목록으로 적는다.
- `docs/design-system/`에 위 증거가 모두 있다.

## 만드는 사람에게 맡기는 것

- 새 파일과 훅, 타입의 정확한 이름.
- 팔레트에 추가하는 단계의 이름과 정확한 값 (위 기준과 매핑 표 검토를 따른다).
- 스타일 캐시 구현 방식.
- 대비 검사 스크립트의 실행 방식과 파일 위치.
- 린트 규칙의 구체적인 선택자.
- 미리보기 화면의 배치와 고정 데이터.
- 이동 요청 하위 폴더를 옮기는 순서와 커밋 단위. 커밋 메시지는 기존 관례(`refactor(fe): ...`)를 따른다.

## 작성자가 정한 것 (사용자가 뒤집을 수 있음)

- 이동 요청 화면이 쓰는 공용 컴포넌트 7개를 범위에 넣는다. 넣지 않으면 다크 모드에서 어두운 카드 위에 라이트 헤더와 배경이 남아 화면이 반쯤만 바뀐다. 대신 이 컴포넌트를 쓰는 다른 화면의 다크 모드 확인이 작업에 추가된다.
- 주차 도면(`features/parking`)은 범위에 넣지 않고 알려진 한계로 적는다.
- 지금 쓰이는 반투명 막과 그림자색은 `overlay.*`, `shadow` 토큰으로 옮긴다.
- 기존 `Colors` / `useTheme()`은 그대로 두고 새 토큰을 옆에 추가한다. 기존 것을 새 토큰으로 대체하는 일은 다른 기능을 옮길 때 한다.
- 고정 스타일 문제는 `createStyles(tokens)` 방식으로 푼다.
- 글자·아이콘 색은 WCAG AA를 기준으로 삼고, 미달인 값은 바꾸는 것을 기본으로 한다. 바꿀지 말지는 행마다 사용자가 정한다.
- 개발 전용 미리보기 화면을 추가한다.
- 테스트 러너는 들이지 않는다.
- 작업은 `master`에서 딴 로컬 브랜치에서 하고 push하지 않는다.
