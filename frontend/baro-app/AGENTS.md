# 주차바로 프런트엔드 개발 지침

이 문서는 사람과 AI가 동일한 구조와 기준으로 작업하기 위한 프로젝트 규칙이다.
새 기능을 구현하거나 기존 코드를 수정할 때 아래 규칙을 따른다.

## 기술 기준

- 이 프로젝트는 Expo SDK 54, React Native, Expo Router, TypeScript를 사용한다.
- 코드를 작성하기 전에 Expo 54 버전 문서를 확인한다.
  - https://docs.expo.dev/versions/v54.0.0/
- 최신 버전이나 다른 Expo 버전의 예제를 그대로 적용하지 않는다.
- Android, iOS, Web에서 함께 동작하는 코드를 기본으로 작성한다.
- 플랫폼별 코드가 필요하면 이유를 명확히 하고 `.ios.ts`, `.android.ts`, `.web.ts` 확장자 또는 `Platform.select`를 사용한다.

## 작업 전 확인

- 작업 전에 관련 화면, 컴포넌트, 훅, 디자인 토큰을 먼저 검색한다.
- 이미 존재하는 공통 컴포넌트나 토큰을 중복해서 만들지 않는다.
- 현재 변경사항을 확인하고 다른 사람의 작업을 임의로 삭제하거나 되돌리지 않는다.
- 백엔드 API 형식이나 중요한 요구사항이 불분명하면 추측해서 확정하지 않는다.
- 새 패키지를 추가하기 전에 기존 의존성으로 해결할 수 있는지 확인한다.

## 폴더 구조

```text
src/
├─ app/                 Expo Router 라우트와 레이아웃
├─ features/            기능 단위 화면, 컴포넌트, API, 훅, 타입
├─ components/ui/       여러 기능에서 공유하는 UI
├─ providers/           앱 전체 Provider
├─ services/            공통 API 클라이언트와 저장소
├─ hooks/               앱 전체 공통 훅
└─ styles/              색상, 간격, 폰트, 반응형 토큰과 웹 전역 CSS
```

### `src/app`

- 라우트 파일과 `_layout.tsx`만 둔다.
- 라우트 파일은 가능한 한 실제 화면을 다시 export하는 얇은 파일로 유지한다.

```tsx
export { default } from '@/features/auth/screens/login-screen';
```

- 컴포넌트, API, 비즈니스 로직, `*.styles.ts`를 `src/app`에 두지 않는다.
- `src/app` 아래의 일반 파일은 Expo Router가 경로로 인식할 수 있으므로 특히 주의한다.

### `src/features`

- 기능별 코드는 `src/features/<feature>`에 둔다.
- 기능이 커질 때만 필요한 하위 폴더를 추가한다.

```text
features/auth/
├─ api/
├─ components/
├─ hooks/
├─ screens/
├─ types/
└─ validation/
```

- 특정 기능에서만 사용하는 컴포넌트는 해당 기능의 `components`에 둔다.
- 여러 기능에서 실제로 공유되는 UI만 `src/components/ui`로 이동한다.
- 단순히 코드가 짧거나 비슷해 보인다는 이유만으로 성급하게 공통화하지 않는다.

## 파일과 이름 규칙

- 파일명은 `kebab-case`를 사용한다.
- React 컴포넌트와 타입 이름은 `PascalCase`를 사용한다.
- 함수, 변수, 훅은 `camelCase`를 사용하고 훅은 `use`로 시작한다.
- 화면 컴포넌트는 `*-screen.tsx`로 작성한다.
- 화면과 라우트에는 default export를 허용하고, 공통 컴포넌트·훅·유틸은 named export를 우선한다.
- 기능 외부 파일을 import할 때는 `@/` 별칭을 사용한다.
- 같은 기능 안에서 가까운 파일을 import할 때는 상대 경로를 사용할 수 있다.
- `any` 사용을 피하고 API 요청·응답 및 컴포넌트 props 타입을 명시한다.

## 스타일 작성

- React Native UI는 `StyleSheet`와 공통 레이아웃 컴포넌트로 작성한다.
- 화면이나 컴포넌트에 로컬 스타일이 있으면 같은 위치에 같은 이름으로 분리한다.

```text
login-screen.tsx
login-screen.styles.ts
```

- 로컬 스타일이 없으면 빈 `*.styles.ts` 파일을 만들지 않는다.
- `global.css`는 브라우저 전용 전역 스타일에만 사용한다.
- 네이티브 화면 스타일을 CSS class에 의존해서 작성하지 않는다.
- 색상, 간격, 폰트, radius, 컨트롤 높이, breakpoint는 `src/styles`의 토큰을 우선 사용한다.

```ts
// 피한다.
padding: 17,
color: '#5144d3',
height: 56,

// 권장한다.
padding: Spacing.md,
color: theme.primary,
minHeight: ControlHeight.lg,
```

- 반복되는 디자인 값을 화면마다 직접 작성하지 않는다.
- 인라인 스타일은 화면 크기나 상태에 따른 동적 값에만 제한적으로 사용한다.
- 고정 숫자를 모두 제거하려고 하지 않는다. 다음 값은 토큰이나 명확한 근거가 있으면 사용할 수 있다.
  - 터치 영역의 최소 높이
  - 아이콘 크기
  - 폰트 크기와 줄 높이
  - 테두리 두께
  - 콘텐츠 최대 너비
  - 이미지 고유 비율
  - 그림자와 애니메이션 값

## Flex와 반응형 레이아웃

- React Native의 기본 세로 Flex 방향을 기준으로 작성한다.
- 일반 화면은 다음 구조를 우선 사용한다.

```tsx
<Screen scroll>
  <ResponsiveContainer>
    <Stack gap={Spacing.md}>{/* content */}</Stack>
  </ResponsiveContainer>
</Screen>
```

- 화면 전체 영역은 `flex: 1` 또는 `flexGrow: 1`로 채운다.
- 주요 콘텐츠는 고정 너비보다 `width: '100%'`와 `maxWidth`를 조합한다.
- 이미지는 가능한 한 `width: '100%'`와 `aspectRatio`로 비율을 유지한다.
- 모바일에서 내용이 잘릴 수 있는 화면은 스크롤 가능하게 만든다.
- 넓은 화면에서 구조가 달라질 때는 `useWindowDimensions`와 `Breakpoints` 토큰을 사용한다.
- 화면마다 `768`과 같은 breakpoint 숫자를 직접 작성하지 않는다.
- `position: 'absolute'`는 배지, 오버레이처럼 레이아웃 흐름에서 분리되어야 하는 요소에만 사용한다.
- 화면 크기에 맞추기 위해 임의의 기기별 width 계산이나 매직 넘버를 추가하지 않는다.

## 공통 UI

- 새 UI를 만들기 전에 `src/components/ui`를 확인한다.
- 현재 공통 레이아웃의 기본 구성은 다음과 같다.
  - `Screen`: Safe Area와 스크롤
  - `ResponsiveContainer`: 반응형 여백과 최대 폭
  - `Stack`: 세로·가로 Flex 배치
  - `AppButton`: 버튼 variant, 크기, 로딩, 비활성 상태
  - `ThemedText`, `ThemedView`: 테마가 적용된 기본 UI
- 공통 컴포넌트는 특정 화면의 문구나 비즈니스 로직을 포함하지 않는다.
- 구조는 같고 색상이나 상태만 다른 컴포넌트는 복제보다 `variant` prop을 검토한다.
- 공통 컴포넌트에 기능별 API 호출이나 라우팅을 직접 넣지 않는다.

## 인증 기능

- 인증 상태는 최소 `loading`, `guest`, `authenticated`로 구분한다.
- 앱 시작 시 저장된 세션 복원이 끝나기 전에 인증 화면을 확정하지 않는다.
- 인증이 필요한 라우트는 Expo Router의 보호 라우트 기능으로 제한한다.
- 로그인 화면에서 API와 저장소를 직접 조작하지 않는다.
  - 화면은 사용자 입력과 상태 표시를 담당한다.
  - API 호출은 `features/auth/api`에 둔다.
  - 로그인·로그아웃 흐름은 인증 훅 또는 Provider가 담당한다.
  - 세션 저장과 삭제는 공통 session storage가 담당한다.
- 비밀번호, Access Token, Refresh Token, 개인정보를 로그에 출력하지 않는다.
- 토큰을 소스 코드나 `EXPO_PUBLIC_*` 환경 변수에 저장하지 않는다.
- 로그인 요청 중에는 중복 제출을 막고 로딩 상태를 표시한다.
- 서버 오류와 입력 검증 오류를 구분하여 사용자에게 표시한다.
- 로그아웃 시 서버 요청의 성공 여부와 별개로 로컬 세션 정리 정책을 명확하게 정의한다.
- 401 처리와 토큰 갱신은 한 곳에서 담당하고 무한 재시도를 방지한다.

## 상태와 API 처리

- 서버 상태, 전역 앱 상태, 화면 로컬 상태를 구분한다.
- 한 화면에서만 사용하는 입력값과 UI 상태는 화면 또는 기능 훅에 둔다.
- 전역 로그인 사용자와 세션 상태는 Auth Provider에서 관리한다.
- API 주소, 요청 필드, 응답 타입, 오류 형식을 백엔드 계약에 맞춰 작성한다.
- API 응답을 화면에서 바로 임의 변환하지 말고 기능 API 또는 mapper에서 처리한다.
- 모든 비동기 화면은 필요한 경우 다음 상태를 고려한다.
  - loading
  - success
  - empty
  - error

## 주석

- 모든 파일이나 모든 함수에 설명 주석을 의무적으로 작성하지 않는다.
- 파일명, 타입, 함수명으로 알 수 있는 내용을 그대로 반복하지 않는다.
- 주석은 코드가 무엇을 하는지보다 왜 그렇게 동작해야 하는지를 설명한다.
- 다음 경우에는 짧은 주석이나 JSDoc을 작성한다.
  - 복잡한 비즈니스 규칙
  - 플랫폼별 예외
  - 세션과 보안 처리
  - 재사용되는 Provider, 서비스, 커스텀 훅의 비명시적 동작
  - 임시 우회 코드의 제거 조건

```ts
// 나쁜 예: 로그인 버튼을 누르면 로그인한다.

// 좋은 예: 세션 복원 중에는 보호 라우트 여부를 판단할 수 없어 전환을 보류한다.
```

- `TODO`에는 가능한 경우 이슈 번호와 제거 조건을 기록한다.

```ts
// TODO(#123): 백엔드 refresh API가 준비되면 임시 갱신 로직을 교체한다.
```

## 접근성과 사용자 경험

- 누를 수 있는 요소에는 적절한 accessibility role과 label을 제공한다.
- 버튼과 입력창은 충분한 터치 영역을 유지한다.
- 색상만으로 상태를 구분하지 않는다.
- 폼 화면은 키보드가 입력창과 제출 버튼을 가리지 않도록 한다.
- 로딩 중인 버튼은 중복 입력을 막고 진행 상태를 전달한다.
- 오류 메시지는 사용자가 다음 행동을 이해할 수 있게 작성한다.

## 검증

- 변경 후 최소한 다음 명령을 실행한다.

```powershell
npm.cmd run typecheck
```

- ESLint 설정이 준비되면 다음 명령도 실행한다.

```powershell
npm.cmd run lint
```

- 테스트 환경이 준비되면 변경한 기능과 관련된 테스트를 실행한다.
- 라우트나 스타일 구조를 변경하면 Web 번들 또는 `_sitemap`에서 잘못된 경로가 생기지 않았는지 확인한다.
- 공통 UI나 플랫폼 스타일을 변경하면 Android, iOS, Web 중 영향받는 플랫폼을 확인한다.
- 반응형 화면은 최소한 작은 모바일 폭과 넓은 화면에서 확인한다.
- 검증하지 못한 항목이 있으면 완료 보고에 이유를 명시한다.

## 작업 완료 기준

- 요구한 기능이 실제로 동작한다.
- 기존 공통 컴포넌트와 토큰을 재사용했다.
- 불필요한 중복과 매직 넘버를 추가하지 않았다.
- 로딩, 오류, 비어 있는 상태를 필요한 범위에서 처리했다.
- TypeScript 오류가 없다.
- 관련 린트와 테스트가 통과했거나 실행하지 못한 이유가 기록되어 있다.
- 임시 파일, 디버그 로그, 민감한 정보가 남아 있지 않다.
- 변경한 파일과 검증 결과를 사용자에게 간단히 설명한다.
