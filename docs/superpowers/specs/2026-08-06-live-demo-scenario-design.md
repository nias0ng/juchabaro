# 발표 라이브 시연 시나리오 — 설계

## 배경

최종 발표에서 실물 장비(젯슨 + 천장 카메라, Raspberry Pi 게이트, RC 모형차 2대,
미니어처 주차장)를 발표장에 세팅하고 **10분 이내의 라이브 시연**을 한다.
차를 직접 조종하며 입차 인식부터 위반 감지, 이동 요청, 해소까지를 실시간으로
보여주는 것이 목표다.

이 문서는 그 시연의 순서, 화면 구성, 사전 준비 작업, 실패 대비를 정의한다.
시연을 위한 개발 항목은 §3에 정리하고, 각 항목의 구현 계획은 별도 문서로 분리한다.

## 시연 구성 결정

### 선택: "전용구역 무자격 주차 + 이중주차" 2사건 구성

시연의 대부분(챕터 1~3)은 **AI 판정 과정**을 주인공으로 하고, 사건 하나(챕터 4,
이중주차)만 **AI 뷰와 사용자 뷰 양쪽**에서 보여준다.

### 왜 이 구성인가

전용구역 위반도 단순 진입이 아니라 주차 확정 뒤 공개한다. 판정 규칙마다 확정 조건이
다르며, 시연에서는 동일한 PARKED 경계를 먼저 설명한다.

| 규칙 | 확정 조건 | 라이브 시연 |
|---|---|---|
| `DISABLED_ZONE_UNAUTHORIZED` / `EV_ZONE_UNAUTHORIZED` | `ZoneVisit INSIDE` + 같은 zone에 `PARKED` + 자격 `false` | 통과·주차 조작 중에는 미확정 |
| `EV_OVERSTAY` | 같은 EV zone에 `PARKED` + `observedAt - parkedAt >= allowedDurationSeconds` (zone 5는 7200초) | 임계값 하향 필요 |
| `BAD_PARKING` / `OUT_OF_ZONE` / `AISLE_BLOCK` | `ParkingEpisode`가 `PARKED` + 규칙별 geometry | 같은 PARKED 경계 사용 |
| `DOUBLE_PARKING` | 피해·방해 차량 모두 PARKED이고 `BlockingRelation`이 `BLOCKING` | 양쪽 주차·관계 확인 시간 필요 |

전용구역은 넓은 polygon을 차량이 통과하거나 주차를 조작하는 동안 bbox가 잠시
겹칠 수 있으므로 `ZoneVisit INSIDE`만으로 사건을 만들지 않는다. PARKED와 동일 zone
assignment를 함께 요구해 Backend 사건의 "주차 위반" 의미를 보존한다. 이중주차는
서비스의 대표 문제(README §1)라 사용자 서사를 감당한다.

`EV_OVERSTAY`는 제외한다. 화면상 아무 움직임 없이 사건만 뜨는 형태라 라이브에서
"지금 판정한 게 맞나"는 의심을 사고, 차량 이동 횟수만 늘린다.

### 시연 조건

| 항목 | 값 |
|---|---|
| 시연 시간 | 10분 이내 (설계 총계 9분 30초, 버퍼 30초) |
| 차량 | RC 모형차 2대, 앱 계정에 등록 |
| 게이트 | RPi 카메라로 실제 번호판 촬영 → OCR |
| 화면 | OBS로 씬 전환, 여러 화면 동시 표시 가능. 앱은 폰 미러링 |
| 영상 송출 | 젯슨은 헤드리스, 노트북에서 네트워크로 수신 |
| 조작 인원 | 최소 3명 (발표 / OBS / RC 조종). RC 조종자는 카메라 프레임 밖 |

### 구역 배치

`hw/jetson/config/zone_definition.json` 기준.

- 일반 주차면 4개 — zone 1, 2, 3, 6
- 장애인 주차면 1개 — zone 4
- EV 충전 주차면 1개 — zone 5 (`allowedDurationSeconds: 7200`, `SLOW`)
- 통행로 1개 — zone 7. 모든 주차면의 `egressZoneIds`가 `[7]`
- 입구 zone 8 (`ENTRY`), 출구 zone 9 (`EXIT`)

## 사전 준비 작업

### 문제: 오버레이와 백엔드 전송이 서로 다른 실행 경로에 있다

현재 코드로는 이 시연을 그대로 돌릴 수 없다.

| 실행 경로 | 오버레이 화면 | 백엔드 전송 |
|---|---|---|
| `src/main.py` (실제 앱) | 없음 — `MonitoringWorker(pipeline)`(`main.py:376`)에 `frame_observer`를 넘기지 않음 | `OutboxPublisherWorker`로 실제 전송 |
| `scripts/watch_live_stream.py` | OpenCV 로컬 창 | 없음 — `JsonlPublicationPreparer()`(`watch_live_stream.py:260`)로 파일에만 기록 |

챕터 4(양 관점)는 오버레이와 앱 알림이 **동시에** 필요하므로 둘을 한 프로세스로
합쳐야 한다. 훅 자체는 이미 있다 — `monitoring_pipeline.py:181`의
`frame_observer(frame, tracking_batch, result)`는 commit 성공 후에 호출되므로,
화면에 그려지는 상태와 실제 커밋된 상태가 항상 같은 프레임에서 나온다.

### 작업 목록

| # | 작업 | 내용 |
|---|---|---|
| 1 | `MonitoringWorker`에 `frame_observer` 통과 | `MonitoringWorker.__init__`에 파라미터를 추가해 `pipeline.run(frame_observer=...)`로 전달 (`src/application/monitoring_worker.py`) |
| 2 | `/live/stream` MJPEG 라우터 | 공유 단일 슬롯 버퍼 + `multipart/x-mixed-replace`. 설계는 `2026-08-03-live-demo-streaming-design.md` §컴포넌트 4에 이미 있음 |
| 3 | 오버레이에 Incident 렌더링 | `live_overlay_renderer.py`의 `_vehicle_status()`(`:172`)는 `ParkingEpisode.state`와 `ZoneVisit.state`만 그린다. `IncidentTransition`을 차량 위 규칙코드 배지 + 상단 사건 배너로 추가 |
| 4 | `.env.demo` 프로파일 | 시연용 임계값. 운영 `.env`는 변경하지 않음 |

**`src/live/live_stream_loop.py`는 시연에 사용하지 않는다.** 자체 캡처 루프를
가지고 있어 실제 앱의 `MonitoringWorker`와 나란히 돌리면 카메라를 두 번 열고
추론을 두 번 한다. 재사용하는 것은 `live_overlay_renderer.py`(렌더러)와 공유 버퍼
개념뿐이다.

### 시연용 임계값

`.env.demo`에서 하향한다.

| 설정 | 운영값 | 시연값 | 근거 |
|---|---|---|---|
| `PARKING_CONFIRM_SECONDS` | 600.0 | 5.0 | 전용구역을 포함한 주차 기반 사건을 시연 시간 안에 확정 |
| `BLOCKING_RELATION_CONFIRM_SECONDS` | `.env.example`에 기본값 없는 필수 설정 | 하향 (D-5에서 확정) | 이중주차 확정 대기 단축 |

`ZONE_ENTRY_CONFIRM_SECONDS=1.0`과 `ZONE_EXIT_CONFIRM_SECONDS=5.0`은 **바꾸지
않는다.** ZoneVisit은 구역 관측을 안정화하고, 전용구역 Incident는 별도의 PARKED
경계를 통과해야 하므로 1초 진입만으로 공개되지 않는다.

### 임계값 하향은 시연 중 먼저 밝힌다

챕터 2의 `PARKED` 전이 시점(2:20)에, 값을 낮췄다는 사실을 **먼저** 말한다.

> "실제 운영값은 10분입니다. 짧은 정차를 주차로 오판하지 않으려고요. 오늘은
> 시연을 위해 20초로 낮췄습니다. 값만 바꿨고 로직은 그대로입니다."

숨겼다가 질문받으면 은폐로 읽히지만, 먼저 밝히면 실측으로 정한 값이라는 인상이 된다.

## OBS 씬 구성

| 씬 | 구성 | 사용 시점 |
|---|---|---|
| **A. 게이트** | RPi가 촬영한 번호판 프레임 + OCR 결과 + 백엔드 응답 (RPi 원격 접속 화면) | 챕터 1 입차 |
| **B. AI 뷰** | `/live/stream` 브라우저 소스 풀스크린 + 좌하단 젯슨 사건 전이 로그 | 챕터 2·3 |
| **C. 양 관점** | `/live/stream` 좌측 60% + 폰 미러링 우상 + 관리자 웹 우하 | 챕터 4 |
| **D. 설명** | 아키텍처 도식 / 파이프라인 도식 | 차량 이동·리셋 대기 중 |
| **E. 백업 영상** | D-3 리허설 녹화본 (챕터별로 분할) | 라이브 실패 시 |

별도의 실물 촬영 카메라는 두지 않는다. 오버레이 화면(`/live/stream`)에 젯슨 카메라의
실시간 영상이 그대로 깔리므로 차량이 움직이는 것이 거기서 보이고, 미니어처 자체는
발표장에서 관객이 직접 볼 수 있다.

씬 A는 별도 카메라가 아니라 **RPi가 이미 촬영한 프레임**을 보여준다. 게이트에
카메라를 하나 더 두는 것보다 OCR의 실제 입력을 보여주는 쪽이 더 직접적인 증거다.
다만 RPi가 촬영 프레임을 화면에 띄우거나 파일로 남기는 경로가 있는지는 D-3 리허설에서
확인해야 한다 — 없으면 로그의 OCR 결과 텍스트만으로 진행한다.

**씬 D가 시간을 만든다.** RC로 차를 옮기는 20~40초는 화면상 아무 일도 일어나지 않는
구간이다. 그 시간에 씬 D로 전환해 시스템 내부 동작을 설명하면 대기 시간이 발표
시간으로 전환된다. 10분 중 약 2분이 여기 해당한다.

### 차량 배치 근거

차2를 챕터 1에서 zone 6(먼 일반 구역)에 임시 주차시키는 이유는 두 가지다.

1. 게이트 왕복을 없앤다. 두 대를 연속 입차시키면 챕터 3에서 게이트로 돌아갈 필요가 없다.
2. 차2를 통행로(zone 7)에 세워두면 챕터 3 이전에 `AISLE_BLOCK` 후보가 잡혀 화면이
   지저분해진다. zone 6에 정상 주차시켜 두면 챕터 3의 `UNPARKED` → 재주차 전이도
   덤으로 보여줄 수 있다.

## 실패 대비

### 폴백 표

| 실패 | 즉시 대응 | 최종 폴백 |
|---|---|---|
| 게이트 OCR 실패 | 1회 재시도 | `REVIEW` 케이스로 전환 — 관리자 웹에서 수동 승인을 보여준다. 실패를 기능 시연으로 바꾼다 |
| 차량 미탐지 / 트랙 끊김 | 씬 D 전환 → 차 리셋 → 1회 재시도 | 씬 E의 해당 챕터 재생 |
| RC 조작 실수 (구역 이탈) | 그대로 두고 `OUT_OF_ZONE` 판정을 보여준다 | 리셋 후 재시도 |
| `BlockingRelation` 미확정 | 차2를 차1 앞쪽으로 조금 더 이동 | 씬 E 챕터 4 재생 |
| 백엔드 전송 실패 / 앱 알림 미도착 | outbox를 보여준다 — 네트워크가 끊겨도 사건이 유실되지 않고 쌓였다가 재전송된다 | 관리자 웹만으로 진행 |
| FCM 푸시 지연 | 앱에서 알림 목록 새로고침 (REST 조회) | |

게이트 OCR 실패와 백엔드 전송 실패는 폴백 자체가 설계 완성도를 보여주는 케이스다.
리허설 때 이 대사를 미리 준비해두면 사고가 나도 시연이 끊기지 않는다.

### 씬 E 확보

D-3 리허설의 성공분을 챕터 단위로 잘라 OBS 미디어 소스로 넣어둔다. 챕터별로 나눠야
실패한 챕터만 교체하고 나머지는 라이브로 계속할 수 있다.

발표장 조명이 리허설 장소와 다르면 탐지 성능이 달라진다. D-1은 가능하면 실제 발표장에서
한다.

## 이 설계가 다루지 않는 것

- **발표 대본 전문.** 챕터별 발표 포인트만 정의했고, 문장 단위 대본은 별도로 만든다.
- **LED·스피커 구현.** 다른 팀원이 개발 중인 기능으로 전제한다. 이 설계의 작업 목록에는
  포함하지 않고, D-3 리허설의 연동 확인 항목으로만 잡는다.
- **`EV_OVERSTAY` 시연.** §시연 구성 결정에서 제외했다.
- **다수 동시 시청자 / 원격 시청.** `/live/stream`은 같은 네트워크의 소수 시청자
  기준으로만 검증한다 (`2026-08-03-live-demo-streaming-design.md` §한계와 동일).
